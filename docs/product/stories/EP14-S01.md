# EP14-S01 — 2FA TOTP admin (login en 2 etapes)

> **HDS-CHECK** (2026-05-29) — Verdict : `OK`
> Periode : NON-HDS (cf. ADR-0003)
> Mots-cles BLOCKED detectes : aucun
> Mots-cles SUSPECT detectes : aucun
> Action : implementable
> Justification : story d'infrastructure d'authentification (TOTP, recovery codes). Aucun vocabulaire metier sante. Touche `User` (compte interne cabinet), pas de donnee de personne concernee.

**Epic** : EP14 — Durcissement securite & conformite (prod V1)
**Priorite** : P1 (risque de lockout admin si le flux 2FA bugue, cf. contradiction documentaire ci-dessous)
**Estimation** : 1.5 - 2 j
**Statut** : **Planned (scope confirme 2026-06-01)** — mode degrade : chiffrement **app-level** du secret TOTP (la solution pgcrypto propre = EP14-S05 fast-follow), trace via log applicatif structure tant qu'EP14-S04 (AuditLog) n'est pas livre
**UC de reference** : `docs/uc/UC-06-2fa-admin.md` (deja redige)

## User story

En tant qu'**ADMIN de cabinet**, je veux **proteger mon compte par un second facteur TOTP**, afin qu'**un mot de passe compromis ne suffise pas a acceder aux donnees clients du tenant**.

---

## Contexte

**Etat verifie (audit code 2026-05-29)** : 2FA **ABSENT** — zero reference `totp / otplib / speakeasy / mfa / authenticator` dans le code. Auth actuel :
- NextAuth credentials (`apps/frontend/src/lib/auth.ts`) → `POST /api/auth/login` (`apps/backend/src/routes/auth.ts`)
- bcrypt compare (rounds 10) + dummy-hash timing-safe (SEC-11) → `signJWT` HS256, TTL 7j (`requireJWT.ts`)
- Login = **1 seul POST**, 3 champs (cabinet / email / password)

**Contradiction documentaire a trancher** : le CDCF D5 (L.185) liste la 2FA en **P0**, mais la checklist securite **S3 la classe P1** (« avant 6 mois », *non bloquant prod*). Recommandation : **P1**, fast-follow post-deadline — pas un soir de go-live (cf. risque ci-dessous).

**Risque majeur** : passer le login a 2 etapes = refonte du flux `authorize()` NextAuth (aujourd'hui mono-POST). Risque de **lockout admin** si bugue. A faire dans une fenetre de test, pas pendant la mise en prod.

---

## Acceptance Criteria

1. Migration Prisma : `User.totpSecret String?` (chiffre at-rest), `User.recoveryCodes String[]` (hashed bcrypt), `User.mfaEnabled Boolean @default(false)`.
2. **Setup** (premier login ADMIN sans MFA) : `POST /api/auth/2fa/setup` genere un secret + `otpauth://` URL → QR affiche cote front.
3. ADMIN scanne (Google Authenticator / 1Password), saisit le code 6 chiffres → `POST /api/auth/2fa/verify` valide via `otplib` (RFC 6238, fenetre 30s) → `mfaEnabled=true` + **10 recovery codes one-shot** affiches **une seule fois**.
4. **Login subsequent** ADMIN : `POST /api/auth/login` (mdp OK) → reponse `{ step: "totp_required" }`, **aucun JWT emis a ce stade**.
5. UI affiche le champ TOTP → `POST /api/auth/2fa/verify` → si OK, JWT signe avec flag `mfaVerified: true`.
6. **Recovery** : TOTP perdu → `POST /api/auth/2fa/recovery` avec un code → JWT emis + code invalide (one-shot, hashed, comparaison constant-time).
7. RBAC : 2FA **obligatoire ADMIN**, optionnelle COMMERCIAL (configurable par tenant en V1.1).
8. Rate-limit dedie sur `/2fa/verify` : 3 essais / 5 min, sinon 429.
9. Trace : entree au setup + a chaque login MFA (depend de l'AuditLog EP14-S04 ; **degrade** : log applicatif structure si AuditLog pas encore livre).

---

## Tests de securite (obligatoires)

- [ ] Setup → QR + secret generes, code valide accepte, recovery codes affiches une seule fois
- [ ] Login mdp OK + TOTP OK → JWT avec `mfaVerified: true`
- [ ] Login mdp OK + TOTP invalide → 401, **aucun JWT**
- [ ] Recovery code one-shot : 2e usage du meme code → 401
- [ ] 4e tentative TOTP en 5 min → 429
- [ ] Un JWT sans `mfaVerified` ne franchit pas les routes ADMIN protegees (si flag enforce)

Fichier cible : `apps/backend/tests/security/2fa.test.ts`

## Notes techniques

- **Lib** : `otplib` (npm, leger)
- **Routes** : `POST /api/auth/2fa/{setup,verify,recovery}`
- **Front** : nouvelle page `/login/2fa` + refonte `authorize()` NextAuth pour gerer l'etape intermediaire (**le point le plus risque**)
- **Chiffrement `totpSecret`** : UC-06 RM3 veut pgcrypto — **or pgcrypto est ABSENT** (cf. EP14-S05 / checklist S2). Option A : chiffrement app-level (cle via env/KMS). Option B : attendre pgcrypto. **A trancher.**

## Dependances

- **pgcrypto** (EP14-S05 / S2) pour `totpSecret` at-rest, OU chiffrement app-level
- **AuditLog** (EP14-S04 / S4) pour la trace — degradable en log applicatif
