# EP12-S01 — Pipeline DnD optimistic update

**Epic** : UI performance — optimistic updates • **Priorite** : Must have • **Estimation** : 2h

## User story

En tant que **commercial**, je veux **que le drag & drop d'une carte dans le pipeline soit instantane** (sans refresh de 2s qui fait disparaitre la carte), afin de **garder une UX fluide quand je deplace beaucoup de dossiers**.

**Diagnostic du bug actuel** : `PipelineView.tsx` L125 → `await loadPipeline()` apres chaque PATCH. `loadPipeline()` fait `setLoading(true)` qui n'occulte pas tout (heureusement) mais le re-fetch complet remplace `data` ce qui force un re-render des `KanbanColumn`. Pendant les ~500ms de la requete (+ rendering React), la carte n'est nulle part visible (elle a quitte la colonne source mais la nouvelle data n'est pas encore rendue dans la colonne cible).

## Acceptance Criteria

### Refactor frontend

1. `PipelineView.tsx` adopte un **optimistic update local** :
   - Avant `apiFetch`, on muts `data` localement : retirer le process de l'ancienne colonne, l'ajouter dans la nouvelle (en gardant ses props identiques sauf `stage`)
   - Si `apiFetch` echoue → revert le state local + toast erreur
   - Si succes → `loadPipeline()` est appele en background (non bloquant : `void loadPipeline()`) pour reconcilier les stats CA
2. Helper `lib/optimistic/movePipelineProcess.ts` :
   - `applyMove(data, processId, fromStage, toStage) : PipelineResponse` (pure function)
   - Recalcule au passage les stats par colonne (count, caPotentiel) pour eviter d'attendre le refetch
3. Le `setLoading(true)` du `loadPipeline()` est conditionne : `setLoading(true)` uniquement sur le **premier** chargement, pas sur les re-fetches
   - Pattern : `loadPipeline({ silent: boolean })` avec `silent=true` pour ne pas mettre `loading=true`
   - Le drag-drop appelle avec `silent: true` ; le mount initial avec `silent: false`

### Refactor force-transition dialog

4. Quand le PATCH 422 (transition invalide), on ouvre le `ForceTransitionDialog` :
   - Le state local doit **revert** la carte a son ancienne position le temps de la confirmation
   - Si l'user confirme `force=true`, on re-applique l'optimistic move + on PATCH avec force=true
   - Si l'user annule, la carte reste a son ancienne place (coherent)

### Recompute stats locales

5. `applyMove()` recalcule :
   - `columns[fromStage].stats.count -= 1`
   - `columns[fromStage].stats.caPotentiel -= process.estimatedAmount`
   - `columns[toStage].stats.count += 1`
   - `columns[toStage].stats.caPotentiel += process.estimatedAmount`
   - `caConfirme` recalcul partiel selon `signedAmount` du process
6. Apres background refetch, les stats sont reconciliees (autoritatif)

## Tests

- Test unit `applyMove` :
  - Move CONTACT → CONSULTATION : process change de colonne, stats updated
  - Move vers une stage absente : no-op safe (return data inchange)
  - Move dans la meme colonne : no-op safe
- Test E2E Playwright :
  - Drag & drop d'une carte → carte visible immediatement dans la colonne cible (assertion `<2s` avec timeout strict 200ms)
  - PATCH 422 + cancel dialog → carte revient a sa colonne d'origine
  - PATCH 422 + force=true → carte reste dans la colonne cible
- Test perf : `loadPipeline({ silent: true })` ne masque pas la pipeline pendant le refetch

## Notes techniques

- Pattern react-query / tanstack-query non introduit ici (overkill au MVP, on reste sur `useState` + helper)
- L'optimistic local est compatible avec le filtre `q`/`qualification` actuel : les filtres restent appliques cote serveur, le local refletera l'etat post-PATCH
- Risque : si l'utilisateur drag pendant un refetch en cours, le nouveau drag peut etre ecrase. Solution simple : `loadPipelineRef.current` debounce, mais MVP : on accepte le rare cas (refetch est court ~500ms)
