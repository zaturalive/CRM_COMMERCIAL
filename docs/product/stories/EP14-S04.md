## User story

En tant qu'**editeur / DPO**, je veux **un journal immuable de qui a fait quoi, ou, comment et quand sur toutes les routes mutantes**, afin de **pouvoir auditer un incident, prouver la conformite RGPD et detecter un usage anormal**.

---

## Contexte

**Etat verifie (audit code 2026-06-01)** : **AUCUN** modele `AuditLog` dans `apps/backend/prisma/schema.prisma`, **aucun** middleware express loggant les mutations. Les seuls logs sont applicatifs (console), non structures, non persistes, non requetables.

**Demande utilisateur (2026-06-01)** : *"il faut qu'on utilise un middleware par-dessus toutes nos routes en envoyant le log de qui fait quoi, ou, comment, quand."* Cette story est la reponse directe.

**Mode degrade (decision Q3 2026-06-01)** : c'est cette story qui porte la trace ideale pour 2FA (EP14-S01) et CGU (EP14-S02). Tant qu'elle n'est pas livree, ces deux stories tracent en degrade (log applicatif structure + ligne `Tenant` pour la CGU).

---

## Acceptance Criteria

1. Migration Prisma : modele `AuditLog { id, userId String?, tenantId String?, method, path, action String?, statusCode Int, ip String?, userAgent String?, bodyHash String?, occurredAt DateTime @default(now()) }`. **Append-only** : aucune route ni service ne fait de `update`/`delete` dessus.
2. Middleware express monte **globalement** (apres `requireJWT`, sur tout le router `/api`) :
   - **Qui** : `userId` + `tenantId` extraits du JWT (null si route publique).
   - **Quoi** : `method` + `path` (normalise, sans query secrets) + `action` derive (ex `process.create`).
   - **Ou** : `ip` (X-Forwarded-For derriere Traefik) + `tenantId`.
   - **Comment** : `userAgent` + `bodyHash` (SHA-256 du body, pas le body en clair) + `statusCode`.
   - **Quand** : `occurredAt` UTC.
3. **Scope** : logue par defaut toutes les mutations `POST / PUT / PATCH / DELETE` + les `GET` sensibles (export RGPD EP14-S06). Les `GET` de listing courants sont **exclus** (volume) — liste configurable.
4. **Sanitization** : aucun champ sensible (`password`, `token`, `totpSecret`, `firstName`, `lastName`, `email`, `phone`, body metier) ne doit apparaitre en clair dans `AuditLog`. Seul le `bodyHash` est conserve.
5. **Non-bloquant** : si l'ecriture du log echoue, la requete metier **n'echoue pas** (log d'erreur applicatif + best-effort). L'audit ne doit pas casser le service.
6. **Multi-tenant** : un audit log est rattache a son `tenantId` ; l'editeur peut lire cross-tenant, un ADMIN ne lit que le sien (route de consultation = fast-follow, hors AC minimal).
7. Retention : conception append-only compatible retention 5 ans (obligation comptable, checklist S4) + export periodique vers stockage immuable (S3 Object Lock) — **l'export froid est du ressort infra**, pas de cette story.

## Tests de securite (obligatoires)

- [ ] POST/PATCH/DELETE sur une route mutation → 1 entree `AuditLog` avec userId/tenantId/method/path/statusCode/occurredAt
- [ ] Le `body` contenant un password / une donnee client → seul le `bodyHash` est stocke, zero plain text
- [ ] Echec d'insertion AuditLog (DB indispo simulee) → la requete metier renvoie quand meme sa reponse normale
- [ ] Un ADMIN tenant A ne peut pas lire les AuditLog du tenant B (quand la route de lecture existe)
- [ ] Aucune route n'expose de `DELETE`/`UPDATE` sur AuditLog (append-only verifie)

Fichier cible : `apps/backend/tests/security/audit-log.test.ts`

## Notes techniques

- **Middleware** : `apps/backend/src/middleware/auditLog.ts`, monte dans `app.ts` apres `requireJWT`, en `res.on("finish", ...)` pour capter le `statusCode` final.
- **Hash** : `crypto.createHash("sha256")` sur `JSON.stringify(body)` apres retrait des cles sensibles.
- **Perf** : insertion asynchrone non-bloquante (fire-and-forget avec catch). Envisager un buffer/batch si volume eleve (mesurer avant d'optimiser — Mantra #37).
- **Derivation `action`** : table de mapping `method+routePattern → action` (ex `PATCH /api/processes/:id/stage → process.stage_change`).
