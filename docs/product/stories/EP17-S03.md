## User story

En tant qu'**editeur**, je veux **gerer les utilisateurs de n'importe quel tenant depuis le Back Office**, afin de **depanner un cabinet (compte bloque, role a corriger, reinitialisation) sans attendre son admin.**

---

## Contexte

**Distinction avec EP15-S02** : EP15-S02 permet a l'**ADMIN d'un cabinet** de gerer **ses propres** users. Ici, l'**editeur** agit **cross-tenant** depuis le BO sur les users de **tout** tenant. Memes operations, acteur et perimetre differents.

**Etat verifie (audit code 2026-06-01)** : aucune route ni UI de gestion cross-tenant des users. Les users sont seedes.

---

## Acceptance Criteria

1. `GET /api/admin/tenants/:tenantId/users` (editeur) : liste les users d'un tenant donne.
2. `POST /api/admin/tenants/:tenantId/users` : cree un compte (ADMIN/COMMERCIAL) avec mot de passe temporaire + `mustChangePassword = true`.
3. `PATCH /api/admin/tenants/:tenantId/users/:id` : desactiver/reactiver, changer le role.
4. `POST /api/admin/tenants/:tenantId/users/:id/reset-password` : declenche une reinitialisation (lien email EP15-S03 ou mot de passe temporaire).
5. Garde "dernier admin" : interdiction de desactiver/retrograder le dernier ADMIN actif d'un tenant.
6. UI BO : page `/admin/cabinets/:id/utilisateurs`.
7. Chaque action est tracee (EP14-S04) avec l'identite de l'editeur.

## Tests de securite (obligatoires)

- [ ] Editeur cree/desactive un user dans un tenant cible → effet correct, action tracee (editeur identifie)
- [ ] Non-editeur appelle `/api/admin/tenants/:id/users` → 403
- [ ] Desactivation du dernier ADMIN actif d'un tenant → refus (garde)
- [ ] User desactive → login refuse
- [ ] L'editeur ne peut pas se faire passer pour un user du tenant sans passer par EP17-S04 (acces support encadre)

Fichiers cibles : `apps/backend/tests/security/tenant-users-admin.test.ts` + e2e BO users
