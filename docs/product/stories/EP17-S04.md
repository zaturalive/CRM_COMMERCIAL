# EP17-S04 — Compte temporaire de support chez un tenant

> **HDS-CHECK** (2026-06-01) — Verdict : `OK avec vigilance`
> Periode : NON-HDS (cf. ADR-0003)
> Mots-cles BLOCKED detectes : aucun
> Mots-cles SUSPECT : acces cross-tenant d'un editeur aux donnees commerciales d'un cabinet. En non-HDS il n'y a pas de donnee Art. 9, mais cet acces doit etre **justifie, borne dans le temps et integralement trace**.
> Action : implementable avec les garde-fous ci-dessous.
> Justification : fonction de support (depannage). Ne cree ni ne manipule de donnee de sante.

**Epic** : EP17 — Back Office editeur (console plateforme)
**Priorite** : P1
**Estimation** : 1.5 - 2 j
**Statut** : Planned (scope confirme 2026-06-01)
**UC de reference** : aucun (a creer : UC-123-support-access)

---

## User story

En tant qu'**editeur**, je veux **ouvrir un acces temporaire dans un tenant pour m'y connecter et diagnostiquer un probleme**, afin d'**aider un cabinet sans lui demander son mot de passe et sans laisser d'acces permanent.**

---

## Contexte

**Etat verifie (audit code 2026-06-01)** : aucune notion d'acces support, d'impersonation ou de compte temporaire. Un editeur ne peut pas se connecter dans un tenant.

**Sensibilite** : c'est la fonction la plus a risque du BO (un acteur exterieur au cabinet accede a ses donnees). Elle exige expiration obligatoire, justification, tracabilite complete et revocation.

**Deux options** :
- **Option A — compte temporaire** (demande utilisateur explicite) : l'editeur cree un compte a duree de vie limitee dans le tenant, puis s'y connecte.
- **Option B — jeton d'impersonation** : pas de compte separe, l'editeur "endosse" une session du tenant via un jeton. Trace plus directe du lien editeur -> session.

Option A retenue par defaut (demande user) ; documenter B comme variante.

---

## Acceptance Criteria

1. `POST /api/admin/tenants/:tenantId/support-access` (editeur) body `{ reason, ttlMinutes }` : cree un compte temporaire dans le tenant, avec `expiresAt`, `isSupport = true`, `createdByEditorId`, et le motif obligatoire.
2. Expiration : a `expiresAt`, le compte est desactive/supprime automatiquement ; toute requete avec ce compte apres expiration est refusee (401/403).
3. Bandeau : pendant une session support, l'UI affiche en permanence "Acces support editeur — tenant {nom} — expire a {heure}".
4. Tracabilite : toutes les actions effectuees via le compte support sont audit-loggees (EP14-S04) avec le lien vers l'**editeur reel** (`createdByEditorId`), pas seulement le compte temporaire.
5. Revocation : l'editeur peut revoquer un acces support actif immediatement.
6. Perimetre minimal : le compte support porte le perimetre strictement necessaire (par defaut lecture ; ecriture seulement si justifiee — a trancher). Il ne peut pas creer d'autres comptes ni elever ses privileges.
7. Transparence (option) : notification au tenant qu'un acces support a eu lieu (date + motif).
8. Un compte `isSupport` ne compte pas comme "dernier admin" et n'altere pas les gardes de gestion des users.

---

## Tests de securite (obligatoires)

- [ ] Acces support cree avec TTL → connexion OK avant `expiresAt`
- [ ] Apres `expiresAt` → acces refuse (401/403), compte inactif
- [ ] Revocation → la session support est coupee immediatement
- [ ] Actions via le compte support → trace pointant l'editeur reel (createdByEditorId)
- [ ] Le compte support ne peut pas creer un autre compte ni s'auto-promouvoir
- [ ] Motif (`reason`) obligatoire, sinon 400
- [ ] Un non-editeur ne peut pas ouvrir d'acces support → 403

Fichiers cibles : `apps/backend/tests/security/support-access.test.ts` + e2e bandeau support

## Notes techniques

- **Migration** : champs `User.isSupport`, `User.expiresAt`, `User.createdByEditorId` (ou table `SupportAccess` dediee si on garde l'historique des acces).
- **Expiration** : verifier `expiresAt` cote `requireJWT` (refus si depasse) + job/cron de nettoyage des comptes expires.
- **Lien d'audit** : propager `createdByEditorId` dans le contexte de requete pour que le middleware EP14-S04 l'enregistre.
