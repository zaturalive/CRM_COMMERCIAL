# EP17-S04 — Acces editeur a un tenant (observation/support autonome)

> **HDS-CHECK** (2026-06-01) — Verdict : `OK avec vigilance`
> Periode : NON-HDS (cf. ADR-0003)
> Mots-cles BLOCKED detectes : aucun
> Mots-cles SUSPECT : acces cross-tenant d'un editeur aux donnees commerciales d'un cabinet. En non-HDS il n'y a pas de donnee Art. 9, mais cet acces doit etre borne, tracable et a perimetre minimal.
> Action : implementable avec les garde-fous ci-dessous.
> Justification : fonction d'observation/support. Ne cree ni ne manipule de donnee de sante.

**Epic** : EP17 — Back Office editeur (console plateforme)
**Priorite** : P1
**Estimation** : 1.5 - 2 j
**Statut** : Planned (scope confirme 2026-06-01)
**UC de reference** : aucun (a creer : UC-123-editor-tenant-access)

## User story

En tant qu'**editeur**, je veux **acceder en autonomie a n'importe quel tenant pour verifier que tout se passe bien**, afin de **ne pas dependre d'un user du cabinet pour qu'il me cree un compte.**

---

## Contexte

**Demande utilisateur (2026-06-01)** : *"un compte admin [editeur] qui puisse acceder a chaque tenant pour voir si tout se passe bien, au lieu d'attendre qu'un commercial lui cree un compte."* Le point cle est l'**autonomie** : l'editeur entre dans un tenant sans friction de provisioning par le cabinet.

**Etat verifie (audit code 2026-06-01)** : pas d'impersonation ni d'acces cross-tenant. Un editeur ne peut pas entrer dans un tenant aujourd'hui.

**Mecanisme retenu** : l'editeur ouvre une **session d'observation** (impersonation liee a son identite) dans le tenant cible, **sans qu'on lui cree un compte**. Perimetre **lecture par defaut** (il vient observer "si tout se passe bien"). Une variante "compte temporaire dedie" est documentee en option.

**Sensibilite** : un acteur exterieur au cabinet accede a ses donnees. Donc : duree bornee, tracabilite complete (identite de l'editeur reel), perimetre minimal, revocation.

---

## Acceptance Criteria

1. `POST /api/admin/tenants/:tenantId/enter` (editeur) : ouvre une session d'observation dans le tenant, **sans creer de compte** dans ce tenant.
2. Session bornee dans le temps (TTL) + revocable a tout moment depuis le BO.
3. Bandeau permanent cote front pendant la session : "Observation editeur — tenant {nom} — expire {heure}".
4. Perimetre **lecture par defaut** (principe de moindre privilege). L'ecriture est activable seulement explicitement + avec un motif.
5. Tracabilite (EP14-S04) : chaque action de la session porte l'identite de l'**editeur reel**, pas un compte anonyme du tenant.
6. Autonomie : l'editeur entre sans qu'un user du cabinet ait a creer quoi que ce soit (c'est le besoin exprime).
7. Sortie : fin de session = retour au BO, l'impersonation s'arrete.
8. Transparence (option) : le tenant peut voir qu'un acces editeur a eu lieu (date + perimetre).
9. Variante documentee : compte temporaire dedie dans le tenant (si on prefere un vrai compte a un jeton d'impersonation).

---

## Tests de securite (obligatoires)

- [ ] Editeur entre dans un tenant → session lecture, action tracee (editeur identifie)
- [ ] Apres TTL ou revocation → acces coupe (401/403)
- [ ] Non-editeur appelle `/enter` → 403
- [ ] Ecriture refusee tant qu'elle n'est pas activee + justifiee
- [ ] L'entree ne cree pas de compte persistant dans le tenant
- [ ] L'editeur n'accede qu'au tenant ou il est entre (pas de fuite cross-tenant pendant la session)

Fichiers cibles : `apps/backend/tests/security/editor-tenant-access.test.ts` + e2e bandeau observation

## Notes techniques

- **Impersonation** : jeton portant `{ editorId, tenantId, scope, expiresAt }`, distinct du JWT normal. `requireJWT` doit le reconnaitre et propager `editorId` au middleware d'audit (EP14-S04).
- **Moindre privilege** : lecture par defaut ; l'ecriture est un mode explicite, trace et motive.
- **Variante compte temporaire** : si retenue, prevoir `User.isSupport`, `expiresAt`, `createdByEditorId` + nettoyage des comptes expires.
