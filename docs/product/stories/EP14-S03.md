## User story

En tant qu'**utilisateur de cabinet**, je veux **acceder a mon espace via `mon-cabinet.vencor-crm.com`**, afin d'**avoir une URL dediee memorable plutot que de saisir le code cabinet a chaque login**.

---

## Contexte

**Etat verifie (audit code 2026-05-29)** :
- Resolution tenant = **par slug saisi au login** (form `tenantSlug` → lookup `Tenant.slug` → `tenantId` dans le JWT). `middleware.ts` front = **NextAuth-only, aucun parsing de host**. Backend resout le tenant depuis le **JWT** (pas depuis l'hote).
- **Substitut deja en place** : la page login accepte `?cabinet=xxx` (URL bookmarkable) + memorise le dernier cabinet en `localStorage`. Donc `vencor-crm.com/login?cabinet=delobaux` fonctionne **deja**, sans dev.

**Nuance historique importante** : le sous-domaine **etait l'intention d'origine** — `EP01-S01` AC#1 dit « la page /login affiche le nom du cabinet **extrait du sous-domaine** » (`cabinet-delobaux.crm.local`). Cette story **realise** cette intention descopee vers le slug lors du fork. Ce n'est donc pas une feature nouvelle mais la **completion** de F01 (« Multi-tenant par sous-domaine », epics.md EP01).

**Point cle** : l'**isolation des donnees ne change pas** — elle reste portee par le `tenantId` du JWT + Prisma `$extends`. Le sous-domaine ne fait que choisir/pre-remplir le tenant au login. C'est pourquoi c'est **non bloquant** pour la prod (P-Could).

**Cout cache (infra, couple D6)** : necessite wildcard DNS `*.vencor-crm.com` + **certificat TLS wildcard** (Let's Encrypt **challenge DNS-01** via l'API DNS Hostinger) + routing Traefik. C'est ce qui en fait un risque le soir d'un go-live.

---

## Acceptance Criteria

1. DNS : enregistrement wildcard `*.vencor-crm.com` (A/AAAA) vers le VPS (couche D6 / infra).
2. TLS : certificat **wildcard** obtenu par Traefik via ACME DNS-01 (Hostinger). Verifie : `https://nimporte.vencor-crm.com` sert un cert valide.
3. `middleware.ts` front : parsing du `host` → extraction du sous-domaine → si present et != `www`/apex → **pre-remplit** le tenant cible.
4. La page `/login` affiche le **nom du cabinet** resolu depuis le sous-domaine (lookup read-only `slug → name`) ; le champ « cabinet » est masque ou verrouille quand le sous-domaine est present.
5. Le login transmet ce tenant ; le backend **valide** que le `tenantSlug` du sous-domaine correspond bien a un tenant actif (sinon page « cabinet inconnu »).
6. **Fallback conserve** : `vencor-crm.com` (apex) garde le formulaire a 3 champs + `?cabinet=` + `localStorage` (zero regression).
7. **Aucune modification** de la logique d'isolation (`tenantId` JWT + Prisma `$extends` inchanges) — a prouver par les tests d'isolation existants qui restent verts.

---

## Tests de securite (obligatoires)

- [ ] `delobaux.vencor-crm.com/login` → affiche « Cabinet Delobaux », login OK
- [ ] Sous-domaine inexistant `inconnu.vencor-crm.com` → page « cabinet inconnu », pas de leak
- [ ] Un user du tenant A logge via `a.vencor-crm.com` ne peut pas lire les donnees du tenant B (isolation inchangee → 404)
- [ ] Spoof : sous-domaine `a` mais `tenantSlug=b` injecte dans le POST → rejet (le backend tranche sur le JWT, pas sur l'hote)
- [ ] Apex `vencor-crm.com` → fallback formulaire 3 champs fonctionne (non-regression)
- [ ] Cert TLS wildcard valide sur un sous-domaine arbitraire

---

## Notes techniques

- **Front** : `apps/frontend/src/middleware.ts` (ajout parsing host, sans casser le `withAuth` NextAuth) + `login/page.tsx` (mode « tenant verrouille »)
- **Back** : endpoint read-only `GET /api/tenant/by-slug/:slug` (nom + actif) pour l'affichage login ; la resolution d'autorite reste le JWT
- **Infra (D6)** : wildcard DNS Hostinger + Traefik ACME DNS-01 — **prerequis bloquant** de cette story
- **Anti-enumeration** : `by-slug` ne doit pas distinguer « inactif » de « inexistant » au-dela du strict necessaire UX
