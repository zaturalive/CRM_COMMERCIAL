## User story

En tant qu'**utilisateur (client/cabinet) ou DPO agissant pour une personne concernee**, je veux **exporter et faire supprimer/anonymiser les donnees**, afin de **respecter les droits RGPD d'acces, de portabilite (Art. 15) et d'effacement (Art. 17)**.

---

## Contexte

**Etat verifie (audit code 2026-06-01)** : **ABSENT** — pas de route `GET /api/me/export`, pas de `DELETE /api/me`, pas de page `/account/privacy`.

**Portee** : deux axes a distinguer :
- **Donnees du compte utilisateur** (le user du cabinet) : export + suppression de son propre compte.
- **Donnees d'une personne concernee** (un `Client` du CRM) : export + anonymisation a la demande, declenche par un ADMIN/DPO du cabinet. C'est le cas le plus probable en pratique commerciale.

L'anonymisation (plutot que delete dur) preserve les stats/CA agreges : remplacer `firstName/lastName/phone/email` par "ANONYMISE", conserver les montants/dates.

---

## Acceptance Criteria

1. `GET /api/clients/:id/export` (ADMIN du tenant) : JSON complet des donnees du client (fiche + process + devis + documents commerciaux + logs de message), scope tenant.
2. `GET /api/me/export` : export des donnees du compte utilisateur authentifie.
3. `POST /api/clients/:id/anonymize` (ADMIN) : anonymise `firstName/lastName/email/phone` du client + cascade coherente, conserve les agregats (montants, dates, CA).
4. `DELETE /api/me` : suppression/anonymisation du compte utilisateur (selon politique — un ADMIN ne peut pas se supprimer s'il est le dernier admin du tenant : A-guard).
5. Page UI `/account/privacy` : bouton "Exporter mes donnees" + bouton "Supprimer mon compte" (confirmation forte).
6. UI fiche client : action ADMIN "Exporter" + "Anonymiser" (confirmation forte).
7. Toute action RGPD est tracee dans `AuditLog` (EP14-S04) — degradable en log applicatif si S04 pas encore livre.
8. Isolation : impossible d'exporter/anonymiser un client d'un autre tenant (404).

---

## Tests de securite (obligatoires)

- [ ] Export client → contient les donnees du tenant courant uniquement, aucun champ d'un autre tenant
- [ ] Anonymisation → `firstName/lastName/email/phone` = "ANONYMISE", montants/dates conserves
- [ ] Cross-tenant : export/anonymize d'un client d'un autre tenant → 404
- [ ] COMMERCIAL tente l'anonymisation → 403 (ADMIN requis) — ou selon RBAC retenu
- [ ] Dernier ADMIN tente `DELETE /api/me` → refus (A-guard)
- [ ] Chaque action RGPD genere une trace

Fichiers cibles : `apps/backend/tests/security/rgpd-self-service.test.ts` + e2e `/account/privacy`

## Notes techniques

- **Anonymisation** vs **suppression dure** : privilegier l'anonymisation pour ne pas casser les FK et garder la valeur statistique. Documenter le choix par entite.
- **Export** : format JSON structure (portabilite Art. 20). Eventuellement zip si documents joints.
- **Cascade** : recenser les tables liees au `Client` (Process, Devis, Document, MessageSendLog, TrackingEvent...) avant d'implementer.
