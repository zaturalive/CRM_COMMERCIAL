## User story

En tant qu'**ADMIN de cabinet**, je veux **creer, desactiver et reinitialiser les comptes de mes commerciaux**, afin de **gerer mon equipe sans dependre de l'editeur a chaque mouvement**.

---

## Contexte

**Etat verifie (audit code 2026-06-01)** : aucune UI ni route de gestion des users cote cabinet. Les comptes sont seedes. Un ADMIN ne peut donc ni ajouter un commercial, ni desactiver un compte qui quitte le cabinet.

**Decision (Q1 2026-06-01)** : 2e niveau du modele de provisioning — l'editeur cree le cabinet + 1er admin (EP15-S01), l'admin gere ensuite ses propres comptes (cette story), **scope a son tenant**.

---

## Acceptance Criteria

1. `GET /api/users` (ADMIN du tenant) : liste les users **du tenant courant** uniquement.
2. `POST /api/users` (ADMIN) : cree un compte `COMMERCIAL` (ou `ADMIN`) avec email + nom + mot de passe temporaire + `mustChangePassword = true` (EP15-S04).
3. `PATCH /api/users/:id` (ADMIN) : desactiver / reactiver un compte (`User.active`), changer le role intra-cabinet.
4. `POST /api/users/:id/reset-password` (ADMIN) : declenche une reinitialisation (lien email EP15-S03, ou nouveau mot de passe temporaire).
5. RBAC : un COMMERCIAL n'accede pas a ces routes (403). Un ADMIN ne peut agir que sur les users de **son** tenant.
6. Garde "dernier admin" : interdiction de desactiver / retrograder le dernier ADMIN actif d'un tenant.
7. UI : page `/config/utilisateurs` (liste + creation + desactivation + reset).
8. Actions tracees (`AuditLog` EP14-S04, degradable).

---

## Tests de securite (obligatoires)

- [ ] ADMIN cree un COMMERCIAL → compte cree dans son tenant, `mustChangePassword=true`
- [ ] ADMIN du tenant A tente de lister/modifier un user du tenant B → 404 (isolation)
- [ ] COMMERCIAL appelle `POST /api/users` → 403
- [ ] Desactivation du dernier ADMIN actif → refus (garde)
- [ ] User desactive → login refuse
- [ ] Escalade : un ADMIN ne peut pas se promouvoir editeur (niveau plateforme hors de sa portee)

Fichiers cibles : `apps/backend/tests/security/user-management.test.ts` + e2e `/config/utilisateurs`

## Notes techniques

- **Reutilisation** : la creation user partage la logique de hash + force-change avec EP15-S01 (factoriser un service `createUserAccount`).
