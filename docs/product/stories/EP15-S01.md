## User story

En tant qu'**editeur de la plateforme (Dimitry / Florian)**, je veux **creer un nouveau cabinet et son premier compte ADMIN**, afin de **pouvoir onboarder un client payant sans passer par le seed de demo**.

---

## Contexte

**Etat verifie (audit code 2026-06-01)** : la creation de tenant et de users se fait **uniquement par le seed** (`apps/backend/prisma/seed.ts`). Aucune UI ni route applicative pour creer un cabinet. Les roles existants sont `ADMIN` et `COMMERCIAL` (le `CHIRURGIEN` a ete retire — ADR-0002). **Il n'existe pas de niveau au-dessus d'ADMIN** : un ADMIN est scope a son propre tenant.

**Decision (Q1 2026-06-01)** : modele **Editeur + Admin a 2 niveaux**. L'editeur opere **cross-tenant** (cree les cabinets), l'admin du cabinet gere ensuite ses propres comptes (EP15-S02). Pas d'inscription publique.

**Point d'architecture sensible** : introduire un acteur cross-tenant dans un systeme aujourd'hui strictement tenant-scope (`tenantId` JWT + Prisma `$extends`). L'isolation des cabinets entre eux ne doit pas regresser ; seul l'editeur franchit la frontiere, et uniquement pour le provisioning.

---

## Acceptance Criteria

1. Niveau editeur : ajout d'un role plateforme (ex `UserRole.EDITEUR` ou table `PlatformAdmin` separee — a trancher dans la story selon impact isolation). L'editeur n'appartient pas a un tenant client.
2. `POST /api/admin/tenants` (editeur seul) : cree un `Tenant` (slug, nom) + le **premier compte ADMIN** (email, nom) du cabinet.
3. Le compte ADMIN cree recoit un mot de passe temporaire (ou un lien d'invitation — depend EP15-S03/email) + flag `mustChangePassword = true` (EP15-S04).
4. Validation : slug unique, format slug (tirets, pas d'underscore — RFC 1035), email valide.
5. RBAC : seul l'editeur peut creer/lister/desactiver des tenants. Un ADMIN client ne voit jamais cette surface (403/404).
6. UI editeur : page `/admin/cabinets` (liste des cabinets + bouton "Nouveau cabinet" + statut actif/suspendu).
7. Desactivation d'un cabinet : un tenant suspendu refuse le login de ses users (sans suppression de donnees).
8. Toute action de provisioning est tracee (`AuditLog` EP14-S04, degradable en log applicatif).

## Tests de securite (obligatoires)

- [ ] Editeur cree un cabinet + 1er admin → le tenant et le compte existent, scope correct
- [ ] ADMIN d'un cabinet appelle `POST /api/admin/tenants` → 403 (pas editeur)
- [ ] COMMERCIAL appelle la route → 403
- [ ] L'admin cree d'un cabinet A ne peut pas lire/modifier le cabinet B (isolation inchangee)
- [ ] Slug en double → 409/400, pas de creation partielle
- [ ] Cabinet suspendu → login refuse a ses users, donnees conservees

Fichiers cibles : `apps/backend/tests/security/provisioning.test.ts` + e2e `/admin/cabinets`

## Notes techniques

- **Decision role** : `EDITEUR` dans l'enum (impacte JWT + middleware) vs table `PlatformAdmin` dediee (isolation plus nette). Documenter le choix et son impact sur `requireJWT` + Prisma `$extends`.
- **Mot de passe initial** : eviter un mot de passe en dur ; generer aleatoire + force-change (EP15-S04), ou invitation par email (EP15-S03).
- **Migration** : ajout du niveau editeur + champ `Tenant.status` (ACTIVE / SUSPENDED).
