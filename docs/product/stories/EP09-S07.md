# EP09-S07 — Retrait section parallele FOLLOWUP du pipeline + lien vers /follow-up

**Epic** : Follow-up dedie • **Priorite** : Must have • **Estimation** : 1h

## User story

En tant que **commercial**, je veux **que le pipeline principal n'affiche plus la section parallele FOLLOWUP** (qui devient redondante avec la page dediee), afin de **garder le pipeline focalise sur la conversion active**.

## Acceptance Criteria

### Frontend pipeline

1. `PipelineView.tsx` : retirer le composant `<ParallelSections>` ou le reduire a la seule section `NON_QUALIFIE`
2. Si on conserve `<ParallelSections>` pour `NON_QUALIFIE` :
   - Renommer en `<NonQualifieSection />` ou laisser `<ParallelSections>` avec une seule prop
3. Header pipeline : ajouter un badge cliquable "X dossiers en follow-up" (count provenant de `/api/follow-up`) qui redirige vers `/follow-up`
4. Le badge est visible meme si le count = 0 (compteur a zero, pas masque)

### API

5. La route `GET /api/pipeline` ne retourne plus la cle `sections.FOLLOWUP` :
   - Reponse `{ columns, sections: { NON_QUALIFIE: {...} }, totalActive, followupCount }`
   - Nouveau champ `followupCount` au top-level
6. La constante `PIPELINE_STAGES` reste inchangee (ne contient pas FOLLOWUP)
7. Le backend continue de maintenir la stage `FOLLOWUP` dans l'enum `ProcessStage` (pas de breaking schema)

### UX transitions

8. Quand on tente de drag une card vers une "ancienne" zone follow-up depuis le pipeline → comportement : drag rejete, toast "Pour passer en follow-up, ouvre le ProcessPanel et utilise l'action dediee"
9. L'action "Passer en follow-up" reste accessible :
   - Dans le ProcessPanel, bouton "Passer en follow-up" (existant, EP04-S04 — il declenche `PATCH /follow-up`)
   - Apres action, redirige optionnellement vers `/follow-up?process=<id>` (toast "Patient passe en follow-up. Ouvre la page Follow-up.")

### Types frontend

10. `PipelineResponse` : retirer `sections.FOLLOWUP`, ajouter `followupCount: number`
11. `STAGE_LABELS` reste — utilise dans plusieurs ecrans (process panel, agenda, etc.)

## Tests

- Test E2E : chargement pipeline n'affiche plus de section follow-up paralelle
- Test integration `GET /api/pipeline` : `sections.FOLLOWUP` absent, `followupCount` present et coherent
- Test : drag d'une card vers une coordonee "ancienne section follow-up" → comportement attendu (rejet ou no-op)

## Notes techniques

- Le composant `<ParallelSections />` actuel gere les 2 sections en tableau — refactor minimal pour ne garder qu'une section
- Garder l'enum `FOLLOWUP` dans `ProcessStage` car beaucoup de code en depend (route `/followup`, processes existants en BDD, transitions)
- Le badge header = simple `<Link href="/follow-up">` avec count provenant du fetch initial
