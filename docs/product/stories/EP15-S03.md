## User story

En tant qu'**utilisateur de cabinet**, je veux **reinitialiser mon mot de passe oublie via un lien recu par email**, afin de **recuperer l'acces a mon compte sans intervention manuelle**.

---

## Contexte

**Etat verifie (audit code 2026-06-01)** : **ABSENT** — aucune route `forgot/reset-password`, aucune page, aucun token de reset. Un utilisateur qui oublie son mot de passe est aujourd'hui bloque. Le backlog §9 classe ce flux "pre-requis pour livrer le projet a un vrai client".

**Provider email (decision 2026-06-01)** : pas de provider payant au demarrage. Deux options retenues — **SMTP auto-heberge** (aucun provider externe) ou **Brevo en offre gratuite**. Le self-service par email s'active quand l'un des deux est branche. **Fallback au demarrage (sans email)** : la reinitialisation est declenchee par un admin (EP15-S02) ou l'editeur (EP17-S03) qui remet un mot de passe temporaire + force-change (EP15-S04) — le go-live n'est pas bloque.

---

## Acceptance Criteria

1. `POST /api/auth/forgot-password` body `{ email }` : genere un token de reset (aleatoire, hashe en base, TTL court ex 1h) et envoie un email avec un lien `/reset-password?token=...`.
2. **Anti-enumeration** : la reponse est identique que l'email existe ou non (pas de fuite d'existence de compte).
3. Page `/reset-password` : saisie du nouveau mot de passe (+ confirmation) + regle de robustesse (longueur minimale, etc.).
4. `POST /api/auth/reset-password` body `{ token, newPassword }` : valide le token (non expire, non utilise), set le nouveau hash bcrypt, **invalide le token (one-shot)**.
5. Apres reset : invalidation des sessions/JWT existants si une revocation est en place (sinon note de dette — voir checklist S5).
6. Rate-limit dedie sur `forgot-password` (eviter le spam d'emails) + sur `reset-password` (eviter le brute-force de token).
7. Le mot de passe temporaire issu du provisioning (EP15-S01/S02) peut emprunter le meme flux.

---

## Tests de securite (obligatoires)

- [ ] Email existant → email envoye, token cree (hashe en base)
- [ ] Email inexistant → meme reponse (200) sans email envoye, pas de fuite
- [ ] Token valide → reset OK, token invalide ensuite (one-shot : 2e usage rejete)
- [ ] Token expire → 400/401
- [ ] Brute-force token → rate-limit 429
- [ ] Nouveau mot de passe trop faible → 400 (regle de robustesse)

Fichiers cibles : `apps/backend/tests/security/password-reset.test.ts` + e2e `/reset-password`

## Notes techniques

- **Token** : aleatoire 32 bytes, stocke hashe (comparaison constant-time), TTL configurable.
- **Email** : interface `EmailSender` (impl SMTP auto-heberge ou Brevo free, interchangeable). Au demarrage sans email, le self-service est inactif et la reinitialisation passe par l'admin/editeur ; le self-service s'active quand l'EmailSender est branche.
- **Migration** : table `PasswordResetToken { id, userId, tokenHash, expiresAt, usedAt }` (ou champ sur User selon simplicite — Mantra #37).

---

## Dependances

- **Email** : SMTP auto-heberge ou Brevo free (pas au demarrage). Au demarrage, fallback reset par admin/editeur sans email — non bloquant.
- EP15-S04 (regles de mot de passe partagees)
