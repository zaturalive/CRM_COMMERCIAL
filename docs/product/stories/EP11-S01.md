# EP11-S01 — Schema TrackingEvent + endpoint stub

**Epic** : Click tracking demo • **Priorite** : Must have • **Estimation** : 1h30

## User story

En tant que **developpeur**, je veux **modeliser et persister les events d'engagement client** (clic sur lien, vue de video, ouverture d'email), afin de **preparer une infrastructure de tracking que les commerciaux peuvent declencher manuellement en mode demo**.

**Note scope** : ce sprint, l'endpoint accepte des events crees manuellement par le commercial ("marquer comme clique"). Aucune redirection externe ne crée d'event automatique.

## Acceptance Criteria

### Schema Prisma

1. Nouvelle table `TrackingEvent` :
   - `id : UUID PK`
   - `tenantId : UUID FK Tenant` (cascade)
   - `clientId : UUID FK Client` (cascade)
   - `processId : UUID FK Process?` (cascade, nullable — un client peut avoir plusieurs process)
   - `eventType : Enum TrackingEventType` (CLICK_LINK | VIEW_VIDEO | OPEN_EMAIL | REPLY_MESSAGE | OTHER)
   - `targetKind : Enum TrackingTargetKind` (MESSAGE_TEMPLATE | DOCUMENT_TEMPLATE | EXTERNAL_URL | CUSTOM)
   - `targetId : UUID?` (FK softlink — pas de FK dure pour permettre flexibilite)
   - `targetLabel : String` (descriptif lisible, ex "Video Mammoplastie J+3")
   - `targetUrl : String?` (URL de la cible si pertinent)
   - `source : Enum TrackingSource` (MANUAL_DEMO | INFERRED | REAL — au MVP, MANUAL_DEMO uniquement)
   - `note : String?` (commentaire du commercial)
   - `userId : UUID FK User?` (qui a cree l'event en demo)
   - `occurredAt : DateTime DEFAULT now()`
   - `@@index([tenantId, clientId, occurredAt])`
   - `@@index([processId, occurredAt])`
2. Nouveaux enums :
   - `TrackingEventType` : `CLICK_LINK`, `VIEW_VIDEO`, `OPEN_EMAIL`, `REPLY_MESSAGE`, `OTHER`
   - `TrackingTargetKind` : `MESSAGE_TEMPLATE`, `DOCUMENT_TEMPLATE`, `EXTERNAL_URL`, `CUSTOM`
   - `TrackingSource` : `MANUAL_DEMO`, `INFERRED`, `REAL`

### API

3. `POST /api/clients/:clientId/tracking-events` :
   - Body Zod : `{ eventType, targetKind, targetId?, targetLabel, targetUrl?, processId?, note? }`
   - `source` est force a `MANUAL_DEMO` au MVP (le commercial valide via UI)
   - `userId` populate via `req.user!.id`
   - Reponse : event cree
4. `GET /api/clients/:clientId/tracking-events?since=<iso>&processId=<id>` :
   - Liste events du client (orderBy occurredAt desc)
   - Filtres optionnels `since` (events apres une date) + `processId`
5. `GET /api/processes/:processId/tracking-events` :
   - Raccourci pour les events lies a un process specifique
6. `DELETE /api/tracking-events/:id` :
   - ADMIN ou createur de l'event
   - Retire un event cree par erreur en demo

### Endpoint stub redirection (preparatoire V1)

7. `GET /api/track/redirect/:trackingId?token=<jwt-light>` (route publique, NE PAS sous middleware auth) :
   - Au MVP : retourne 501 NOT_IMPLEMENTED avec message "Tracking redirection non active en mode demo"
   - Architecture preparee pour V1 : recevoir un token JWT light qui contient `{ clientId, processId, targetKind, targetId, targetUrl }`, creer un `TrackingEvent` automatique, puis 302 vers `targetUrl`
   - Au MVP : on documente l'archi mais on n'active pas le 302

## Tests

- Test integration : POST event manuel → cree, retourne le event
- Test integration : GET filtré par `processId` retourne uniquement les events de ce process
- Test integration : tenant isolation — userTenantA ne peut pas creer d'event pour clientB
- Test integration : `GET /track/redirect/:id` retourne 501 au MVP
- Test integration : DELETE par non-createur non-ADMIN refuse 403

## Notes techniques

- `targetId` n'est pas FK dur (Prisma permet cela en utilisant `String?` brut) — flexibilite necessaire pour pointer vers MessageTemplate, DocumentTemplate, ou un futur entite
- L'endpoint redirection est documente meme si non actif au MVP — evite une migration breaking en V1
- Pas de cron de purge au MVP (TrackingEvent reste indefiniment) — V1 prevoira une retention
